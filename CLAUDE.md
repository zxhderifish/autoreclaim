# AutoReclaim — agent operating instructions

This repo is **public CODE only**. The user's personal data — category profile, queue,
history — lives in a separate PRIVATE repo `autoreclaim-data`. PII (`pii.enc`) is never in
any repo; it stays local on the user's machine.

## Routing — decide this FIRST, before any other action

Work out which job you're doing before you touch anything:

- **Setup / onboarding** — a human asks to "set up" / "install" / "get started", OR
  `../autoreclaim-data/profile.json` does not exist yet → **invoke the `autoreclaim-onboard`
  skill** and follow it. Do NOT start fetching settlements, writing files, or improvising
  setup steps. Onboarding is a guided chat; the skill drives it. If data already exists
  (profile.json, queue.jsonl, or a scheduled task), onboarding runs in UPDATE mode — never
  overwrite an existing profile/queue/schedule without showing the user what's there and
  getting their OK.
- **File this week's claims** — "file my claims", "process the queue", "review what you
  found" → **invoke the `autoreclaim-confirm` skill**.
- **Scheduled weekly discovery** — you were launched by the `autoreclaim-weekly` task (or
  the cloud Routine) with no human in the loop → follow the **Discovery flow** below.

When a human is interactively asking to get started, it is ALWAYS onboarding — never the
discovery flow. The discovery flow is for the unattended scheduled run.

## Discovery flow (scheduled run)

The weekly task / cloud Routine clones the data repo and sets `AUTORECLAIM_DATA_DIR` to the
`autoreclaim-data` checkout.

1. Set up: `python3 -m venv .venv && .venv/bin/pip install -e .`
   Make sure `AUTORECLAIM_DATA_DIR` points at the `autoreclaim-data` checkout.
2. Fetch raw pages: `.venv/bin/python -c "from autoreclaim.fetch import fetch_all; from autoreclaim.clean import html_to_text; import json,sys; print(json.dumps({k: html_to_text(v) for k,v in fetch_all().items()}))" > sites.json`
3. **You (the agent) read `sites.json` AND the user's profile** (`$AUTORECLAIM_DATA_DIR/profile.json` — it has `keywords` = the user's deliberate picks, `common_pack` = broad defaults almost everyone has, optionally `state` = the user's US state, and optionally `ruled_out` = brands/categories the user has said DON'T apply to them — answers given during a confirm session, sunk back so they're never asked twice; treat a `ruled_out` brand as a hard non-match even if it's also in the common pack). **Extract efficiently — don't grep-thrash:** sites.json is keyed by domain; go site-by-site in ONE pass — for a small site read it through once, for a large one grep it ONCE for all profile brands to find the relevant blocks and read those; don't re-grep per brand or re-read repeatedly. **Grep traps:** match brands on WORD BOUNDARIES — `chase` is inside "purchased", `target`/`max`/`meta`/`delta` are common English words; use generous context windows (entries on these list pages run 400–600 chars, a tight window decapitates the neighboring entry); ignore brand hits in site footers/social-link blocks (every site links facebook/twitter/youtube). **Junk resistance:** some sources carry affiliate bait ("get $15 now", survey/cash-app signups) — NEVER treat those as settlements and NEVER put an affiliate link in the digest; only official settlement-site links belong in `claim_url`. For EACH open settlement, judge **semantically** whether this user might qualify — use synonyms, product lines, and the eligibility conditions in the description, NOT just keyword overlap; treat `common_pack` brands CONSERVATIVELY (match only if the settlement clearly targets that brand, mark it low confidence), match `keywords` normally. A brand hit is NOT a match if the class is wrong (e.g. the user's brand but a settlement for that company's *employees*, *job applicants*, or *commercial equipment buyers*). If the profile has `state`, use it: a settlement scoped to another state is a clear non-match; one scoped to the user's state is a better match. **Data-breach settlements (hard evidence):** run `.venv/bin/python -m autoreclaim.breach` (no args — it reads EVERY email in `profile.json`; the schema supports `emails: [...]` and the legacy single `email`) to get the companies whose breaches the user is ACTUALLY in (free XposedOrNot lookup, no key). Breach names need normalizing: map them to companies ("LuminPDF" → lumin pdf) and ignore generic non-company entries (e.g. "scraped"). Match any open data-breach settlement targeting one of those companies and mark it HIGH confidence — even if the company isn't in keywords/common_pack — and say so in eligibility_reason (e.g. "Your email was in the X breach"). **Notice/ID-gated settlements (second hard-evidence source):** many settlements (especially data-breach ones) are filed with a Class Member ID / Claim ID + PIN from a notice the administrator emailed or mailed to class members. If an email search tool is callable, search the user's inbox for such notices (settlement name, administrator name, "Class Member ID" / "Claim ID"). Notice FOUND → the user is definitively in the class: mark HIGH confidence, put the ID into `class_member_id`, and say so in eligibility_reason ("Found the settlement notice in your email"). Notice NOT found but the settlement is ID-gated → they may still qualify: mark LOW confidence and say in eligibility_reason that filing needs the ID from their notice or the site's lookup form. **Never put the PIN anywhere** — not in settlements.json, not in the queue; the filing step re-reads it from the email. Write ONLY the ones the user might qualify for into `settlements.json`: a JSON list where each item has keys: `source`, `title`, `category_tags` (lowercase words a person would recognize), `deadline` (ISO or null), `claim_url` (the http link to file — links survive in the cleaned text as "text (https://…)", so grab the URL near the settlement; this is the link the user clicks to file manually, so always capture it; PREFER the official settlement-admin site — if a listing only links the aggregator's own detail page, fetch that detail page once to pull the official URL from it, and only fall back to the aggregator page if that fails, saying so in eligibility_reason; if the listing has no link, search once for the official settlement-administrator site and use that; if no official site can be found either, the listing is probably aggregator filler — set null, mark LOW confidence, and say so in eligibility_reason), `class_member_id` (only when the notice scan found an ID, else omit), `needs_proof` (bool), `attestation_strength` ("normal"/"strict"/"unknown"), `est_payout` (the INDIVIDUAL user's estimated payout — "up to $X" / "$X–$Y" / "pro-rata share"; NOT the total settlement fund. If only a total is stated, note it in eligibility_reason and give the per-person estimate, or null), plus your judgment: `eligible` (true), `eligibility_reason` (one human sentence, e.g. "You bank with Chase"), `confidence` ("high"/"medium"/"low"). **Open ≠ fileable:** aggregators list cases as "open" that are actually registration-only — no claims process yet, funds in escrow (e.g. the domestic-airline antitrust case). Telltales: deadline "Varies"/"Pending", "register for updates", "claims process to be announced" — queue them if relevant but say "registration only — no claims process yet" in eligibility_reason and cap confidence at medium. Leave `id` out — the pipeline computes it. Be generous on recall (the user confirms before filing); skip only clear non-matches and anything past its deadline.
4. Run the pipeline and write the queue + digest:
   `.venv/bin/python -m autoreclaim.run_discovery settlements.json sites.json`
   This reads `profile.json` and writes `queue.jsonl` inside `$AUTORECLAIM_DATA_DIR`, and prints the digest body (empty if nothing new). Passing `sites.json` makes the digest report unreachable sources — "no new finds" and "a source was down" must never look the same. The digest includes each settlement's `claim_url` so the user can file manually.
5. Notify the user. Cloud Routine → send the digest via the **email connector** (subject: "AutoReclaim weekly digest"). Local Mode-1 task → post a desktop notification (macOS: `osascript -e 'display notification "..." with title "AutoReclaim"'`). **Whenever you show the user a table of finds, include a "Claim link" column with the `claim_url`** so they can reclaim manually if they want.
6. In the `autoreclaim-data` repo, commit the updated `queue.jsonl` and push.
7. **If any step fails, still notify the user** with what failed (notification or email). A run that dies silently is indistinguishable from "nothing new this week".

Never put PII anywhere. The scheduled discovery only discovers/matches/notifies — it does not file claims (filing happens locally via the `autoreclaim-confirm` skill).
